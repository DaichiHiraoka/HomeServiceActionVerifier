対象：`README.md` `rule.md` `論文_プロト.md` `論文_プロト_v2.md` `卒業研究_実験計画.md`（＋repo実装状況）。2026-07-02時点。

## 総合判定

**計画は卒業研究として妥当かつ完了可能。** 「意図の推定」を避けて「観測可能な文脈逸脱の2値分類」に落とした問題設定、アブレーション（A–F）＋文脈長比較＋早期検知という実験設計、失敗時の解釈方針（§9.2）まで用意されている点は、卒研の計画として水準以上。ただし下記の**致命的になりうるリスク3点**（特徴量の循環、ショートカット学習、実装の未着手）への対処が成否を分ける。

## 1. 技術スタックの妥当性

### 現状

| 層 | 選定 | 評価 |
| --- | --- | --- |
| 姿勢推定 | MediaPipe (>=0.10) | ○ CPU動作・無料・単人固定カメラの前提に合致。33点2D/準3D |
| 映像入出力 | OpenCV | ○ |
| 分類器 | RF / SVM / LightGBM（計画上） | ◎ ~90系列に対して深層学習を避けた判断は正しい |
| 実装 | `お試し/skeleton_grip_detector.py`（手21点の把持判定プロト）のみ | △ 後述 |

### 指摘

1. **新方針の実装はほぼゼロ。** `src/` に残っているのは旧方針の `.pyc` キャッシュのみで（`.py` は legacy へ移動済み）、全身骨格パイプライン・特徴量抽出・実験ハーネスは未着手。`お試し/` は手の把持判定であり、本実験の主入力（全身骨格系列＋物体位置）とは別物。**7月中にend-to-endの最小パイプライン（動画→骨格CSV→特徴量→分類→指標）を1本通すこと**が最優先。stale な `.pyc` は削除推奨（混乱の元）。
2. **スマホRTSPリアルタイム構成（SYSTEM_ARCHITECTURE.md）は研究本体には不要。** 主張はすべてオフライン評価で検証できる（Time-to-detection も録画に対する逐次推論で計算可能）。データ収集は「普通に録画→オフライン処理」に簡素化し、リアルタイムデモは余裕があれば最後に。
3. **MediaPipe Pose の弱点を計画に織り込む。** しゃがみ・後ろ向き・机の陰で関節が欠損する。①カメラ位置を事前テストで決める（実験計画に「姿勢推定ができる位置」とあるが定量確認を）、②欠損フレームの補間方針を決める、③骨格推定失敗率をデータ品質として論文に記載する。単人・固定カメラなら代替（YOLO-pose, RTMPose）への乗り換えも1日で可能なので、ここで悩みすぎない。
4. **物体側は手動アノテーションで開始する方針（Step 2）は正しい。** 自動化するなら ArUco マーカーを小物に貼る手が最も安く、検出精度の議論を丸ごと回避できる（「物体検出は本研究の主眼でない」と明記済みなので整合する）。
5. 依存に LightGBM / scikit-learn が未追加（`pyproject.toml` は mediapipe/opencv/numpy のみ）。些末だが早めに。

**2D由来の限界**：手先-物体距離は画像座標系なので奥行き曖昧性がある。カメラ角度依存は §Step 5 で誤分類要因として既に想定されており、論文上は「限界」として書けば十分。

## 2. 手法・実験計画の妥当性

### 良い点

- 「窃盗検出」でなく「作業文脈から逸脱した物品操作の検出」への再定義（プロトv2 §分類対象）は、定義可能性・倫理・実験実施可能性の全てで正しい。
- 条件A–Fのアブレーション＋文脈長スイープ＋早期検知評価という3軸は、仮説「単発動作では不足、文脈で改善」を直接検証する構造になっている。
- 成立条件を事前に数値で置いている（F1+0.10、Recall≥0.70、FPR≤0.20）。事前登録的で良い。
- LOPO評価を最初から入れている。

### リスクと対処（重要度順）

**R1. 特徴量の循環（最重要）。** 条件Eの「返却有無」「作業領域への復帰」は、不自然系列の**ラベル定義そのもの**（「元に戻さない」「作業に戻らない」）と一致している。これを人手でアノテーションして入力にすると「ラベルをラベルで予測する」ことになり、Eの勝利が自明化して査読・質疑で崩れる。→ これらの特徴は**必ず骨格座標と物体bboxから自動計算で導出する**（例：物体最終位置と初期位置の距離、接触終了後Nフレームの体幹位置と作業領域中心の距離）。「手で付けた意味ラベル」は入力に入れない、を実装ルールにする。

**R2. ショートカット学習。** 演技シナリオは系列ごとの「台本」が分離しすぎ、モデルが「出口方向に歩いた＝不自然」のような表層特徴を拾うだけで高精度が出てしまう恐れがある。→ **交絡シナリオ（hard negative）を通常側に追加する**：「工具を取りに一度出口方向へ移動して戻る」「小物を身体近くに保持して運ぶが作業場所に置く」等。実験計画4.2の「探索」はこの役割を果たせるので、プロトv2の3種に削らず**通常4種（探索込み）を維持することを推奨**（v2と実験計画でシナリオ数が3/3と4/4で不整合になっている点も要統一）。誤分類分析（Step 5）でショートカットの有無を明示的に検査する。

**R3. n=90・演者3人での統計的主張の弱さ。** LOPO 3-fold は分散が大きく、「F1が0.10以上高い」が偶然の域を出ない可能性がある。→ ①演者は可能なら5人へ（実験計画の「望ましい目安」側に寄せる）、②系列単位のbootstrapでF1の信頼区間を出す、③乱数シード複数回の平均±SDを報告する。この3つで学生研究としては十分堅くなる。

**R4. クラス比50/50の非現実性。** 実運用では不自然系列は稀であり、FPR 0.20は「5回の通常作業で1回誤警報」を意味し実用上は高い。→ 実験としてはこのままで良いが、論文で「均衡データ上の評価であり、低事前確率環境ではPrecisionが大きく低下する」ことを限界として一段書く。閾値非依存の**ROC-AUC / PR-AUCを評価指標に追加**しておくと防御しやすい。

**R5. 「早期予測」（タスク3・4）は独立タスク化しない。** 主分類器をスライディングウィンドウで逐次適用してスコア曲線を出し、閾値超え時刻を Time-to-detection として集計すれば、同じモデルでタスク3・4が両方カバーできる。別モデルを立てると工数が倍増する。

**R6. プライバシー主張との整合。** 条件F（局所クロップ）はクロップサイズ次第で「部屋が写る」ので、クロップの最大サイズを仕様として固定し論文に明記する。また「骨格でも歩容再識別が可能」という限界は `docs/プライバシー配慮_根拠資料.md` §5 の通り先回りして書く。

**その他**：撮影は人を被写体とするため、所属大学の倫理審査・同意書の要否を指導教員に早めに確認（骨格のみ保存という設計自体が同意取得を容易にする）。

## 3. 学生レベルでの完了可能性

**結論：完了可能。ボトルネックは実装とアノテーションであり、データ収集ではない。**

工数見積り（1人・週15–20h想定）：

| 作業 | 見積り | 備考 |
| --- | --- | --- |
| 最小パイプライン実装（動画→骨格→特徴→分類→指標） | 3–4週 | 最優先。7月中 |
| 撮影環境構築＋パイロット撮影 | 1週 | カメラ位置・骨格取得率の確認込み |
| 本収集（90–150系列） | 撮影自体は2–3日 | 演者3–5人の日程調整が律速 |
| アノテーション（接触区間・物体bbox） | 2–3週 | 90系列×数点/系列なら現実的。ArUcoなら大幅短縮 |
| 特徴量・比較実験（A–F＋文脈長） | 3–4週 | 条件はパイプラインの入力切替で実現できる設計に |
| 早期検知評価・誤分類分析 | 2週 | R5の方式なら軽い |
| 執筆 | 6–8週 | プロトv2が既に骨子なので着手は早くできる |

7月開始→12月末実験完了→1–2月執筆・発表で収まる。**やらないこと（§12）が明文化されているのが最大の完了可能性担保**。追加でスコープを守るためのルール：物体検出の自動化・リアルタイム化・多人数対応・実宅環境多様化は、主実験が終わるまで着手しない。

### 最短の次アクション

1. `src/` の stale `.pyc` を整理し、新方針のパッケージ骨格を作る
2. MediaPipe Pose で1本の録画から骨格CSVを出すスクリプト（`お試し` の手検出コードを流用可能）
3. ダミー2系列（自分で演技）で特徴量→LightGBM→F1 まで貫通させる
4. パイロット撮影でカメラ位置と骨格取得率を確定 → シナリオ台本を凍結（R2の交絡シナリオ込み）
