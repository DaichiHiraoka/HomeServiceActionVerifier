致命的な問題
1. 評価が循環している。 正解ラベル(label: high_risk など)はアノテーション時に人間が付けますが、その判断根拠(object_owner=resident、container_owner=worker、zone=private_desk)も同じ人間が同じ行に手書きします。ルールエンジンはその手書きフィールドだけを読んで採点します。つまり「正解を導いた情報そのもの」を入力に使っており、高精度になるのは設計上の必然です。私が前のターンで机上検証して「Video A は全部 0.0、Video B は全部検出」と予測できたこと自体が、実験する前から結果が決まっている証拠です。

2. 「比較手法」が同一関数のラッパーになっている。 token_only.py と proposed.py を読むと、どちらも run_rule_based をそのまま呼び、メソッド名とメモを付け替えているだけです。compare-methods は同じ数値が3行並ぶ表を出力します。これを比較結果として発表すると、審査側には一目で見抜かれます。

3. 一番難しい問題を「所与」としている。 実映像から action、object_class、特に object_owner(これが bag_context ペアを分ける唯一の特徴量)を推定する部分が全て未実装です。「鍵が住人の物か作業者の物か」は映像だけからはほぼ判別不能で、この研究の最重要仮定なのに、ドキュメントのどこにも「実システムでは誰がこのトークンを作るのか」の答えがありません。審査で確実に突かれます。

4. その帰結として、現状の手法構成では動画を撮っても数値が1つも変わりません。 rule_based / token_only / proposed はいずれも映像を一切読まず、annotations.jsonl だけで結果が決まります。私が作った撮影計画も、この構造を引き継いでいます。動画はデモと記録としては価値がありますが、「実験データ」としては現状機能しません。

優先順に挙げます。いずれも卒研の期間で実行可能です。

主張を「検出性能」から「情報価値の分析」に組み替える。 「どの情報があれば文脈逸脱を判定できるか」が元々の研究目的なので、それを正面から実験にする: WorkOrder から owner 情報を抜いたら/ゾーン情報を抜いたら/作業票自体を抜いたら(これが本来の token_only)、どの指標がどれだけ落ちるかのアブレーション比較。これなら循環があっても「ラベルを再現するのに必要な最小情報は何か」という正当な問いになり、比較表に意味が生まれます。実装も rule_engine の入力を削るだけです。

2. 正解ラベルの付与をトークン記入から手続き的に分離する
