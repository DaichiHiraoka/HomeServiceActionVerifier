Home Service Action Verifier 研究・実験構成ガイド

卒業研究用 PoC ― リポジトリ構成・実験設計・手法比較の解説資料(2026年6月版)

1. このリポジトリは何か

Home Service Action Verifier は、一般家庭内で許可済みの作業者(例: Wi-Fi ルーターの修理担当者)が作業を行う場面を対象に、 「依頼された作業の範囲から外れた行動」をイベント単位で検出できるかを検証する研究用 PoC です。 動画全体をブラックボックスで分類するのではなく、イベント単位の構造化情報(EventToken)を、許可内容を機械可読化した作業票(WorkOrder)と照合し、 各イベントを normal / review / suspicious / high_risk の4ラベルで評価します。

研究の問い: 許可された作業の範囲から外れた行動を、どの情報で検出できるか。 特に、作業票・所有者・許可エリア・撮影対象といった文脈情報のうち、どれが判定に寄与するかを数値比較で明らかにする。

本システムは犯罪や不正行為を断定しません。顔認識・個人識別・人物属性推定・自動通報は実装せず、raw video を外部 API へ送信しない設計を制約として明文化しています。 出力はあくまで「人手確認に回すべき許可外行動の候補」です。

2. 研究スコープ ― 何を評価し、何を評価しないか

逸脱検出の全体問題は、(a) 映像からイベント情報を抽出できるか(知覚)と、 (b) イベント情報が与えられたとき逸脱を判定できるか(推論)の2つに分かれます。

本研究の評価対象は (b) 推論 です。イベント情報(EventToken)が与えられた条件下での判定可能性を評価し、 映像からの抽出(物体検出・行動認識・所有者推定)は対象外とします。 このスコープ宣言により、「どの情報が判定に必要か」という問いに評価を集中させます。

補足: したがって rule_based / token_only / アブレーション変種は動画ファイルを入力として使用しません。 動画はデモ・記録・将来の VLM 実験用です(README 制限事項に明記)。

主要モジュールの役割

モジュール役割
schemas.pypydantic による型定義。EventToken(イベント情報)、WorkOrder(作業票)、ZoneConfig(ゾーン座標)、DetectionResult(判定結果)、EventEvaluationMetrics(評価指標)、RuleWeights(重み・閾値設定)を一元管理する。

rule_engine.py基準手法。EventToken を WorkOrder と照合して加点式スコア(0.0〜1.0)を計算し、閾値で4ラベルへ変換する。アブレーションフラグで特定情報に依存する規則だけを停止できる。
baselines/token_only.py対照手法。WorkOrder を意図的に参照せず、EventToken の汎用情報のみで判定する。「許可文脈なしで何が判定できないか」を示す。
event_evaluation.pyイベント単位の評価。二値指標(suspicious / high_risk を positive)、同一動作・異文脈ペアの判別精度、review 率、予測欠落・余分予測の集計を行う。
cli.py実験の入口。解析(analyze-scenario)、評価(evaluate-events)、複数手法比較(compare-methods)を提供し、使用した重み・語彙警告を config.json に記録して再現性を担保する。

5. 手法比較 ― なぜこれが「研究としての比較」になるのか

各手法は「使える情報の量」だけが異なり、判定の枠組みは共通です。 そのため手法間の性能差は、そのまま「その情報の寄与」として解釈できます。 これは「どの情報で検出できるか」という研究の問いを、そのまま実験条件に写像した構成です。

手法使う情報比較で分かること
token_onlyEventToken のみ(作業票なし)許可文脈なしの限界。撮影対象の許可・禁止ゾーンを判定できず、文脈不明イベントは review に逃げる。
rule_basedEventToken + WorkOrder(全情報)基準線。作業票との照合で文脈を判定した場合の性能。
rule_based_no_owner所有者情報を除く所有者情報の寄与。「住人の物を作業者バッグへ」の検出が崩れるか。
rule_based_no_zone禁止ゾーン情報を除く許可エリア情報の寄与。禁止エリア系イベントの recall が落ちるか。
rule_based_no_photo_target撮影許可対象を除く撮影対象情報の寄与。型番撮影と書類撮影の区別が消えるか。
rule_based_no_action_allowlist許可行動リストを除く「作業票にない行動」加点の寄与。
proposed将来: 曖昧イベントのみ VLM 補助現状は rule_based と同一結果のため、主比較から除外(VLM 接続後に追加)。
vlm_direct_full / roi将来: イベント窓フレーム比較枠のみ。未接続(明示的に未実装エラー)。

検証する仮説(research_protocol §6.5): H1 owner 情報を除くと bag_context ペアの判別精度が低下する。 H2 zone 情報を除くと禁止エリア系イベントの recall が低下する。 H3 photo_target 情報を除くと photo_context ペアの判別精度が低下する。

6. なぜこの設計が必要か

6.1 同じ動作でも文脈で意味が変わる

本研究の中心的な難しさは、行動ラベルだけでは正常と逸脱を区別できないことです。 注釈では同一動作・異文脈のイベントを same_action_pair_id で結び、ペア単位で判別精度を測ります。

ペア同じ動作正常な文脈逸脱の文脈区別に必要な情報
photo_contextphotograph(撮影)ルーター型番ラベルを撮影住人の私的書類を撮影撮影許可対象リスト(作業票)
bag_contextplace_into_container(収納)作業者の工具を工具バッグへ戻す住人の鍵を作業者バッグへ入れる物体と収納先の所有者情報
drawer_contextopen(開ける)―(作業対象の操作)作業対象外の私物机の引き出しを開ける許可・禁止エリア情報

token_only はこれらのペアを構造的に判別できません(例: どちらの撮影も同スコアで review になる)。 rule_based が判別でき、対応するアブレーション変種で判別が崩れることを示せれば、 「その情報が判別に必要である」という主張が実験的に支持されます。

6.2 循環構造を避けるための2つの仕掛け

問題: 正解ラベルの判断根拠(所有者・ゾーンなど)と、検知器の入力フィールドを同じ人が同じ注釈行に書くと、 検知器が正解の導出根拠をそのまま読むことになり、高精度が設計上の必然になってしまいます(循環構造)。

対策:

  1. ラベル付与手続きの分離(research_protocol §3.5): 正解ラベルは動画のみを見て「依頼された作業の範囲か」を判断して付与し、作業票や EventToken の他フィールドは参照しない。トークン記入とラベル付与は別パスで行い、付与日を記録する。
  2. 差分で測るアブレーション: 絶対精度は循環の影響を受けうるが、「情報を抜いたときの性能低下幅」という条件間の差分は、その情報の寄与そのものであり、循環の影響を受けない。

7. ラベルとスコアの定義

ラベル意味二値評価での扱い
normal作業票・許可エリア・作業対象と整合する通常行動negative
review低中スコアで人手確認に回す行動デフォルト除外(3ポリシーすべて報告)
suspicious作業票や許可文脈から外れる可能性が高い行動positive
high_risk住人所有物を作業者バッグへ入れる等、強い確認が必要な行動positive

Rule-Based のスコアは加点式(禁止ゾーン +0.4、住人私物 +0.4、住人所有物の操作 +0.3、住人物の作業者側収納 +0.8、許可外撮影 +0.5、作業票にない行動 +0.25、高リスク物体 +0.2)で 1.0 を上限とし、 閾値 0.2 / 0.5 / 0.8 で4ラベルへ変換します。重みと閾値は RuleWeights として設定ファイル化されており、デフォルト値の根拠は今後の感度分析で検証する位置づけです。

8. 評価指標の読み方

指標意味と注意点
accuracy / precision / recall / f1 / false_alarm_rate二値評価(suspicious・high_risk = positive)。confusion matrix とともに出力。
same_action_different_context_accuracy同一動作・異文脈ペア内のイベントを正しく分けられた割合(4クラス完全一致基準)。深刻度の取り違え(suspicious と high_risk の混同)も不正解に数える。
same_action_different_context_binary_accuracy同ペア指標の二値基準版。「検出できたか」と「深刻度を当てたか」を分離して解釈するために両方を報告する。
review_rate予測が review になった割合(分母は注釈イベントに対応した予測のみ)。review はデフォルトで二値評価から除外されるため、不確実な判定へ逃げた量を別途可視化する。token_only はこの値が高くなる設計である。
num_events_without_prediction / num_predictions_without_event予測が欠落したイベント数と、注釈に存在しない余分な予測数。欠落は coverage の問題として集計し、ペア指標の正誤計算からは除外する(黙殺しない)。
roc_auc / average_precision二値評価対象が30件以上、かつスコアのユニーク値が4種類以上の場合のみ出力。小規模・離散スコアでは統計的に意味を持たないため、初期デモでは件数・per-event 表・confusion matrix を中心に解釈する。

9. 現在の限界

  • 知覚層は未実装: 実動画からの物体検出・手検出・所有者推定は stub であり、EventToken は人手注釈で与える。特に所有者情報(object_owner)の実システムでの出所(事前の私物登録・持込申告など)は設計上の今後課題。
  • データ規模: 1シナリオ(router_repair)・台本付きの少数イベントであり、統計的な性能主張はできない。本段階は「実証」ではなく「実現可能性確認」と位置づける。
  • 台本化された逸脱: 実際の逸脱行動はより目立たないはずで、分布が異なる。
  • VLM 比較は未接続: proposed の VLM 補助、vlm_direct 系は比較枠のみ。
  • 重み・閾値の根拠: RuleWeights のデフォルト値は暫定であり、感度分析が未実施。
  • ゾーン定義: 固定矩形の仮座標であり、実動画の画角に合わせた調整が必要。

10. 今後の課題

  1. 約50秒の動画を2本撮影する(正常版 / 要件外行動を含む版)。撮影計画は docs/researcher_next_steps/filming_plan.md に定義済み。違反版にはペアの両文脈を含め、ペア指標を1本で評価できる構成とする。
  2. アブレーション比較(H1〜H3)を実行し、情報寄与の差分を主結果としてまとめる。
  3. トークンへのノイズ注入(所有者・ゾーンの確率的誤り)で、上流認識の不完全さに対する頑健性を評価する。
  4. イベント窓フレームを用いた VLM-direct を接続し、「構造化トークン+作業票」対「生映像+VLM」の対比を行う。
  5. 関連研究(映像異常検知・行動認識・コンプライアンス検査・VLM 映像理解)との位置づけを整理する。
  6. 監視される側である作業者の同意・誤検知の不利益など、作業者側の倫理的配慮を文書化する。
